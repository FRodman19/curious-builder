# Short demo and complete workflow

## Explain the choice

When the mode is unclear, use a question like:

“Would you like a short product demo that shows the key actions and results, or a complete workflow that follows the whole task through its panels, settings, AI exchanges and export? Both use the real UI with clear on-screen guidance. The complete version takes the time needed to make each step understandable.”

A clear request for either mode, or an earlier choice, is enough. Do not repeat the question. If both are requested, make separately labeled contact sheets and exports. Do not generate a second mode merely because it exists.

## Shared fidelity

No shortcuts that invent how the interface works. Inspect the actual app/code, recordings or approved designs before choreographing the task. Sidebars and tools are part of the interface: opening a panel, selecting its tab, changing a setting, applying it and seeing the result must follow the supported path. Use the correct agent identity, mode and controls when AI appears. Do not arbitrarily substitute another provider or call a generic chat panel the actual integration.

A condensed interval is different from a missing interaction. Mark time compression in the review notes. A reconstructed workflow remains a reconstruction; an unbuilt feature remains a labeled concept. For a Blender task, for example, verify its version, workspace, selected object, mode, actual panel and operator before demonstrating a modeling or export step. Do not replace it with a generic editor or a magic one-click result.

## Short product demo

Define one viewer takeaway. Establish the app context, show the relevant real control, perform the key action and show its result. Setup already completed can be omitted only if the starting state is clear. Condense waiting; keep enough time to understand the result. Individual feature loops and grids are valid, with each card completing its own cycle. Do not speed up everything or cut between unrelated endpoint images.

## Complete workflow demo

Define the specific task boundary and final output. Inventory the full connected UX before the contact sheet:

- Starting project/media state and entry point
- Navigation and sidebar/tab changes
- File selection, important settings and previews
- Exact prompt, submission, working state, proposal and approval where AI is involved
- Supported failure and recovery states relevant to the requested example
- Applied changes visible in every affected surface
- Final review, export settings, progress and output

Account for every necessary transition. A caption cannot replace a missing click or panel. A success toast cannot replace the visibly changed canvas, timeline or output. Include representative errors when requested or central to the workflow, not every possible failure in one forced sequence.

Use storyboard rows with state, actual control, action, response, source evidence, caption and allotted time. Follow [pacing and moving review](production.md#pacing-and-moving-review); never infer actual processing speed from a condensed demo.

## Captions outside the UI

Default to one clear centered page/action heading on the brand backdrop outside the device/window. An additional action-caption strip is optional; omit it when the user prefers titles only, and preserve clear action/result cues. Narration does not automatically require burned-in subtitles. If using action captions, place them below a desktop window, and above or below the entire phone frame on mobile. Never place it over the phone screen or bezel. Omit decorative dots and bottom progress bars. See [caption and device framing](caption-and-device-framing.md). Keep it outside the app chrome so viewers do not mistake it for a product control. Reserve the caption band in the layout rather than covering the timeline. Maintain consistent alignment, size, contrast and safe margins.

Examples: “Open the Audio panel”, “Choose the external recording”, “Review the proposed cuts”, “Apply the changes”, “Return to Edit”, “Export the finished clip”. Name the actual action; avoid generic praise or vague labels. Minimal punctuation. Update the caption when the action changes. Keep a concept label separate and unobtrusive where required. Each independent grid card needs its own action label if one shared label would be ambiguous.

## Review each mode on its own

Before presenting the sheet, confirm panel and navigation continuity, readable captions, exact targets and state preservation. After animation, inspect normal-speed playback and encoded action boundaries. Complete mode fails review if required UX steps disappear between screenshots. Short mode fails if its condensation makes the action misleading or hard to follow. Report omitted or unverified steps explicitly.


## Camera style is not workflow scope

Record scope, camera treatment (whole-device/window or frameless detail), presentation shell and aspect ratio separately. “Complete” does not imply zooms. Reuse existing choices.

Whole-device/window mode is the default: fit the entire frame inside the safe canvas, preserve navigation context, and animate actions within the viewport. Scrolling is native app movement, not permission to clip the hardware. Keep the centered heading outside the phone. No mandatory zoom accompanies a click, save or page change.

When detail mode is appropriate, transition to a clearly frameless app/component view instead of pushing half the phone out of frame. Preserve source proportions, target/result relationships and enough context to identify the component. Return to the complete device when location matters. A purely whole-device request remains stable; do not silently add detail mode.

Keep page/action headings readable outside product chrome and camera transforms. Do not add slide/chapter counters or production badges. Titles-only means no second caption strip. Material version or concept labels can remain where needed; evidence, fixture and capture notes belong in sidecars. A heading must not claim an action absent from the animation.
